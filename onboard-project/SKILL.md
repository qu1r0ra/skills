# Onboard project

Produce a project-owned resource for a particular audience and mission. Projects may involve code, research, operations, or other work. Before planning content or reviewing a resource, read the common sections and matching task branches in [authoring-guide.md](references/authoring-guide.md); it owns the researched authoring rules and their limits.

## 1. Inspect the project

Find the owning repository and its instructions, project facts, source materials, existing onboarding resources, and persisted audience or author preferences. Distinguish authoritative project evidence from examples and historical proposals. Read existing resources for reusable facts and explicit local decisions; carry their audience and medium only when the current mission warrants them.

Done when the project sources and current preferences have locators, and missing facts are separated from choices only the owner can make.

## 2. Confirm the brief

Use [grill-qu1r0ra](../grill-qu1r0ra/SKILL.md) to resolve the material choices, using inspected evidence to avoid asking for discoverable facts. Reuse settled answers from this run; for a new run or changed mission, present persisted preferences for confirmation where they affect the result.

The brief records:

- Mission: why these people need the project, and what successful onboarding enables.
- Audience: roles, subject expertise, project familiarity, prerequisites, likely misconceptions, and access needs. An expert can be new to this project.
- Outcomes: what readers should be able to explain, evaluate, or do, with observable evidence appropriate to each outcome. Translate an aim such as “understand” into those expectations with the owner.
- Scope: essential project concepts, boundaries, exclusions, authoritative sources, and facts still missing.
- Delivery: medium, package location, navigation, expected use, self-containment, available time, and constraints such as offline use or an external venue.
- Preferences: tone, depth, practice/feedback, diagrams, citations, and any project-specific requirements. Recommend reversible defaults for flexible choices and explain the consequential ones.

Done when the owner confirms the brief, including audience, mission, outcomes, scope, format, and the remaining open questions. A confirmed brief already supplied in the session satisfies this step. Persist it in the project's existing design or onboarding convention before authoring.

## 3. Close evidence gaps and plan

Read [teaching-principles.md](references/teaching-principles.md) for the relationship to upstream `teach`. Map each outcome to its project evidence, prerequisites, explanation or example, and an appropriate way to try or inspect the intended performance. Choose depth and support from this audience's starting point.

Inspect project evidence first. When a material factual or authoring-method gap remains, invoke [research-qu1r0ra](../research-qu1r0ra/SKILL.md) with narrow questions, allowed context, primary-source expectations, and a bound of one sweep plus one gap-fill round. Project materials stay within their authorized context; public research briefs receive only the context needed for their questions. The authoring guide supplies the general method; research only the gaps relevant to this run.

Record unresolved claims and decide whether they can be labelled and excluded from essential outcomes. An essential unresolved fact blocks the affected content; return to the owner if it requires their decision. If a dependency is unavailable, name it and the affected step rather than silently substituting another workflow.

Done when every outcome has a source-backed content path and a suitable check, and each remaining gap has an explicit disposition.

## 4. Author

Follow the confirmed brief and the authoring guide. Use the chosen medium's authoring skill when needed. Provide a clear entry point, prerequisite route, project-specific explanations, and supporting reference material sufficient for the agreed standalone use. Keep essential content and assets in the agreed package; external reading extends it according to the brief.

Use explanations, worked examples, comparisons, exercises, or feedback where they serve an outcome. Self-checks may be optional and answers may remain freely available; agree any gating with the owner. Format, quizzes, custom visuals, and beginner-level exposition are choices made in the brief.

Done when the complete package and brief are persisted in the project, every essential claim has a traceable source, and each planned outcome is covered.

## 5. Verify and hand over

Check factual correspondence with project sources, prerequisite order, audience fit, outcome coverage, citations, and remaining uncertainties. Exercise the package's promised navigation, rendering, examples, and offline behavior as applicable. Use repository checks and the chosen medium's verification workflow. A resource review verifies the artifact; claims about learner mastery require actual learner evidence.

Fix material findings, then report the package's entry point, intended audience/outcomes, checks performed, and any unresolved limitation. Resource production ends here. For ongoing live teaching or individual learning records, explain that the owner can invoke `teach` separately.

Done when the package passes the relevant checks and the owner receives its location and known limits.
